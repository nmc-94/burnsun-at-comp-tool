Entry screens — implementation reference

Three screens are locked. Everything below is what it cost to build them — the shell change they forced, the states they did not cover, and the one convention they contradict.

Built. Every open question below carries the answer it was given. The code is SignInScreen.tsx, teams/FirstTeam.tsx, teams/TeamPicker.tsx and styles/entry.css; this stays as the record of what was decided and why, not as a to-do list.

1 · What is locked

ScreenNameWas
Signed outField — mark, wordmark, label, button. Nothing else.landing-signin #5
No teamName it — one question, one oversized input.post-signin #3
On teamsStraight through — most recent team as a door, rest as a footnote.post-signin #8

The three exploration files are superseded and worth keeping only for provenance: landing-iterations.html, landing-signin-iterations.html, post-signin-iterations.html.

2 · The shell consequence

This is the largest item and it is structural, not cosmetic. Today App.tsx renders one shell for every route:

  • .app-shell — max-width: 720px; margin: 8vh auto
  • .app-header — wordmark, product label, and UserChip
  • <main> — the route, or SignedOut
  • .app-footer — the health line and the theme toggle

Signed out must leave the shell entirely

Field has no header, no footer and no 720px column. It cannot be a card inside <main> — the signed-out branch has to render instead of .app-shell. Three things follow from that, and all three are real losses that were accepted by locking Field:

  • The header sign-in button goes. Good: UserChip currently renders one and the old card deliberately did not, to avoid two controls with the same name. Field's own button calls signIn() directly.
  • The theme toggle goes while signed out. applyTheme persists to localStorage and index.html re-applies it pre-paint, so a returning user keeps their choice. A first-time visitor gets system and no way to override until they are signed in.
  • The health line goes. If the API is down, sign-in fails with nothing on screen explaining why.
Decided — the footer went, both occupants moved

The theme toggle moved into the header, so it exists on every signed-in route including the workspace, where the footer had it before. Signed out still has neither, and that loss stands: a returning visitor keeps their choice out of localStorage, a first-time one gets system.

The health line became a banner that only renders when the probe fails, full-bleed under the header rather than in a footer nobody scrolls to. It frames the probe's own words rather than printing them raw — TypeError: Failed to fetch is not a sentence. The footer element is gone entirely, and with it data-testid="app-footer".

Signed in gets a full-bleed header

Screens 2 and 3 use .appbar — full width, 14px block padding, a 1px bottom border. The current .app-header is inside the 720px column, has no border, and sits 8vh down the page.

The workspace route already goes full-bleed via .app-shell-wide. So adopting .appbar on the teams route makes the two more consistent, not less — but it is a change to base.css and the shell, not just to TeamList.tsx.

Decided — one header for every signed-in route

.app-header is the appbar now: full-bleed, bordered, wordmark linking home. .app-shell became a full-height flex column and the 720px column moved off it onto <main> as .main-column, so the teams screen can opt out with .main-full without a second shell. isWide() was not touched — route.test.ts pins teams as not-wide, and the workspace keeps its own height: 100dvh override.

It wraps by row below about 620px. A bar holding a wordmark, a theme control and a character with two sign-out buttons does not fit a phone on one line, and a bar that scrolls sideways takes the whole page with it.

4 · Data

Every value on these screens is something the API already returns. Nothing needs inventing.

ScreenReads
Signed outSession.ssoEnabled
No teamSession.character.characterName; createTeam(name)
On teamsTeam.name, .yourLevel, .updatedAt, .archived; Session.character
Decided — sorted client-side

"Straight through" promotes the most recently edited team. comptool/teams.py sorts with .order_by(Team.name), so the API returns teams alphabetically. TeamList reorders by updatedAt descending on arrival rather than changing the query: at this size it costs nothing, and alphabetical is still what the endpoint's other callers want.

The tag reads "Most recent", not "last opened", deliberately: updatedAt is when anyone last edited the team, and there is no per-character last-opened anywhere in the schema. If "last opened by you" is what is actually wanted, that is new state to persist.

Decided — the existing rule was scoped, not broken

Screen 3 shows "edited 2 hours ago". CommentThread.tsx explicitly rejects relative timestamps: "a relative time that is rendered once and never re-rendered goes quietly wrong the longer a board stays open", and formats absolute instead via toLocaleString.

That reasoning is about a long-lived surface. The teams screen is on for the few seconds it takes to pick a board, so a phrase there cannot drift far enough to mislead. lib/ago.ts carries the scoping in its docblock; absolute stays the default anywhere a screen outlives its own strings. It takes now and locales as parameters rather than reading the ambient clock, which is the only reason it is testable.

5 · The states the mocks did not draw

The three locked screens cover the three happy paths. These are everything else, and what each one was given:

StateAs built
ssoEnabled: false Same layout, one muted line. Mark, wordmark and tag stay put; the button's slot holds the explanation instead. A button that could only ever 503 is worse than no button, and this screen is otherwise nothing but the button — so the sentence has to take its place rather than sit beside it.
Session loading The same slot again, as role="status": "Checking your session…". Measured at 9px of movement when it becomes the button, so the page does not jump.
Teams loading / error A centred role="status" line where the promoted block goes, and role="alert" beneath it. TeamList also clears error with the list it belonged to — left standing, one failed load kept its message through every later success.
Archived teams A chip at the end of the footnote row, and a quiet text button on "Name it" — without the second one, archiving your only team strands it, because restore lives on the team's own settings screen. Archived teams replace the screen rather than joining it: archived is a switch, not an include, so the two sets are never in hand at once.
Create-team failure role="alert" under the form on both screens. Not duplicate names — an earlier draft of this row claimed those; there is no unique constraint on Team.name and create_team does no lookup, so no 409 exists. The real cases are 401 and 5xx. maxLength and the blank guard are load bearing: they are exactly the server's two constraints, and a 422 that slips past them arrives with an array-shaped detail that messageFor cannot unwrap.
"Sign out everywhere" Kept. The mock's bar showed only "Sign out"; dropping the second control would have been a regression against REQUIREMENTS §5.3. The bar has room, so UserChip renders both, restyled.
Character portrait The real buildCcpPortraitUrl(characterId, 64). The initials .avatar above was only ever there to keep the mock offline.
Long character names Not anticipated here at all, and found at 430px: the name wrapped to three lines and "everywhere" fell off the right edge. The name truncates and the bar wraps by row.

6 · Tokens

No new colours. Every surface, line and text value is tokens.css verbatim. Three custom properties are added, all derived from --accent so a rebrand carries them:

TokenWhy
--on-accentText on an amber fill. Dark in both themes: paper-white on light's #c47a1e is 3.3:1, short of AA for a 15px label. Dark gives 5.4 light / 9.1 dark.
--haloThe glow under the two primary buttons.
--halo-farThe page wash behind screens 1 and 3.

On §6.4. REQUIREMENTS bans gradient, blur, glow and drop shadow "in application UI" and reserves them for "marketing/landing surfaces". Screen 1 is squarely a landing surface. Screens 2 and 3 are application UI and spend only two things: a --halo-far page wash and a --halo shadow under the single primary button. Kept — locking the screens as drawn was taken as the sign-off. Both are still one declaration each, in styles/entry.css, and deleting either changes no layout.

7 · Accepted inconsistency

Screen 2 is left-aligned in a 720px column; screens 1 and 3 are centred. A given character only ever sees one of 2 or 3, so the two never sit side by side — but the flow signed-out → first team → returning does go centred, left, centred. Shipped that way, because both were locked as drawn. Cheapest reconciliation if it starts to grate: centre screen 2's block and keep the oversized input.
